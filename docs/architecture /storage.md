# Storage Architecture

> Storage design and disk allocation standards for the Enterprise Reference Architecture.

## Purpose

This document defines the storage architecture and disk allocation standards used across the Enterprise Reference Architecture.
The design provides a consistent two-disk model for Linux workload VMs while maintaining a clear separation between the operating system and persistent workload data.

The primary goals are:

* separation of OS and workload storage
* predictable VM deployment
* controlled filesystem growth
* easier backup and recovery
* simplified storage expansion
* efficient use of limited physical hardware
* consistent storage standards across infrastructure roles

---

## Storage Principles

The storage architecture follows these principles:

1. **Separate the operating system from workload storage**

   * Disk 1 contains the core operating system files.
   * Disk 2 contains additional system filesystems and role-specific persistent data.

2. **Use LVM for flexible storage management**

   * Both OS and data storage can be managed using LVM where appropriate.
   * Logical volumes provide flexibility for future capacity adjustments.

3. **Keep variable system data away from the OS root filesystem**

   * `/var`, `/home`, and `/tmp` are located on Disk 2.
   * This reduces the risk of these filesystems consuming the root filesystem.

4. **Use role-specific storage**

   * Workload-specific data is placed on Disk 2.
   * Examples include PostgreSQL data and Docker application data.

5. **Use a two-disk baseline**

   * General Linux VMs use two virtual disks.
   * Database and Docker workloads may receive a larger second disk.

6. **Avoid unnecessary storage complexity**

   * Additional virtual disks are not introduced unless a clear operational or performance requirement exists.

7. **Storage separation is independent from network segmentation**

   * Disk and filesystem separation provide storage isolation.
   * Network isolation is implemented separately through VLANs, firewall policies, and security zones.

---

# Standard Two-Disk Model

Linux workload VMs follow the following general model:

| Disk   | Primary Purpose                           | Standard Size |
| ------ | ----------------------------------------- | ------------: |
| Disk 1 | Core operating system                     |         20 GB |
| Disk 2 | System filesystems and role-specific data |        20 GB+ |

The **20 GB** size is the baseline for general-purpose VMs.
The second disk should be increased for workloads with significant persistent data, particularly:

* PostgreSQL
* Docker
* application repositories
* persistent application volumes

---

# Disk 1 — Operating System

Disk 1 is dedicated to the core operating system.

The standard layout is:

```text
Disk 1
├── EFI System Partition
├── /boot
└── LVM Physical Volume
    └── vg_os
        └── lv_root
```

### EFI System Partition

The EFI System Partition contains the bootloader files required for UEFI boot.

Typical mount point:

```text
/boot/efi
```

### `/boot`

The `/boot` filesystem contains:

* Linux kernels
* initramfs files
* bootloader-related files

### `vg_os`

The remaining usable space on Disk 1 is assigned to the `vg_os` volume group.

The standard OS logical volume is:

```text
vg_os
└── lv_root
```

### `lv_root`

Mount point:

```text
/
```

The root filesystem contains the core operating system and system directories that are not separately mounted.
The root filesystem is intentionally kept separate from `/var`, `/home`, and `/tmp`.

---

# Disk 2 — System and Workload Storage

Disk 2 contains filesystems that are separated from the root filesystem as well as role-specific persistent data.

The standard structure is:

```text
Disk 2
└── LVM Physical Volume
    └── vg_data
        ├── lv_var
        ├── lv_home
        ├── lv_tmp
        └── Role-Specific Logical Volume(s)
```

The exact role-specific logical volume depends on the VM.

---

## `lv_var`

Mount point:

```text
/var
```

`/var` contains variable system data such as:

* system logs
* package caches
* service state
* spool data
* application-generated system data

Separating `/var` prevents uncontrolled growth in logs or service data from consuming the root filesystem.

---

## `lv_home`

Mount point:

```text
/home
```

`/home` contains local user home directories.
Keeping `/home` outside the root filesystem provides independent capacity management for user data.

---

## `lv_tmp`

Mount point:

```text
/tmp
```

`/tmp` is used for temporary files generated by the operating system and applications.
Separating `/tmp` limits the impact of temporary data growth on the root filesystem.

---

# Role-Specific Storage

After the standard system filesystems are allocated, remaining capacity in `vg_data` can be assigned to workload-specific logical volumes.
The logical volume name should clearly describe its purpose.

Examples:

```text
vg_data
├── lv_var
├── lv_home
├── lv_tmp
└── lv_pg_data
```

or:

```text
vg_data
├── lv_var
├── lv_home
├── lv_tmp
└── lv_app_data
```

This allows the storage architecture to remain consistent while adapting to the VM's role.

# Database Storage

## db01

`db01` hosts PostgreSQL and therefore requires dedicated database storage.

The standard layout is:

```text
db01
│
├── Disk 1
│   ├── EFI
│   ├── /boot
│   └── vg_os
│       └── lv_root
│
└── Disk 2
    └── vg_data
        ├── lv_var
        ├── lv_home
        ├── lv_tmp
        └── lv_pg_data
```

### PostgreSQL Data

The PostgreSQL data volume is:

```text
vg_data
└── lv_pg_data
```

Typical mount point:

```text
/var/lib/postgresql
```

The exact PostgreSQL data directory may vary depending on the PostgreSQL version and distribution packaging.
The important architectural requirement is that PostgreSQL persistent data resides on the dedicated `lv_pg_data` logical volume rather than on the root filesystem.

### Why PostgreSQL Uses the Second Disk

Database storage is separated from the OS because database data can grow significantly over time.

This provides:

* independent database capacity management
* reduced risk of filling `/`
* clearer backup boundaries
* easier storage expansion
* better operational visibility

A **third PostgreSQL disk is not part of the standard architecture**.
Additional storage can be introduced later only if actual workload requirements justify it.

# Application Storage

## app01

`app01` hosts containerized applications and therefore requires persistent application storage.

The standard layout is:

```text
app01
│
├── Disk 1
│   ├── EFI
│   ├── /boot
│   └── vg_os
│       └── lv_root
│
└── Disk 2
    └── vg_data
        ├── lv_var
        ├── lv_home
        ├── lv_tmp
        └── lv_app_data
```

The application data volume is:

```text
vg_data
└── lv_app_data
```

A suitable mount point can be:

```text
/opt/app-data
```

The final Docker directory and volume structure should be defined in the Docker deployment documentation.

Potential persistent data includes:

* Forgejo repositories
* Keycloak data
* NetBox data
* OpenBao data
* Portainer data
* Wiki.js data
* application configuration
* Docker volumes
* other persistent container data

# General Linux Infrastructure VMs

Infrastructure VMs such as `ipa01` use the same baseline architecture.

```text
VM
│
├── Disk 1
│   ├── EFI
│   ├── /boot
│   └── vg_os
│       └── lv_root
│
└── Disk 2
    └── vg_data
        ├── lv_var
        ├── lv_home
        └── lv_tmp
```

Additional role-specific storage can be added to `vg_data` when required.
This keeps the storage architecture consistent across the environment.

# Storage Allocation

The baseline allocation is:

| Workload         | Disk 1 | Disk 2 | Storage Focus             |
| ---------------- | -----: | -----: | ------------------------- |
| General Linux VM |  20 GB |  20 GB | OS + standard filesystems |
| FreeIPA          |  20 GB |  20 GB | Identity services         |
| PostgreSQL       |  20 GB | Larger | `lv_pg_data`              |
| Docker host      |  20 GB | Larger | `lv_app_data`             |
| Automation       |  20 GB | 20 GB+ | Automation data           |

The exact size of each logical volume should be determined according to the VM role and expected workload.

---

# Storage Expansion

The LVM-based design allows storage to be expanded without changing the overall architecture.

For a workload using Disk 2:

```text
Disk 2
   │
   ▼
Physical Volume
   │
   ▼
vg_data
   │
   ▼
Logical Volume
   │
   ▼
Filesystem
```

When additional capacity is required:

1. Expand the virtual Disk 2.
2. Resize the LVM physical volume.
3. Extend `vg_data`.
4. Extend the appropriate logical volume.
5. Expand the filesystem.
6. Verify available capacity.
7. Verify the application or service.

For example, PostgreSQL expansion follows:

```text
Disk 2
   ↓
vg_data
   ↓
lv_pg_data
   ↓
PostgreSQL filesystem
   ↓
PostgreSQL data
```

The same principle applies to application storage on `app01`.

# Filesystem Standards

Filesystem selection should be based on the Linux distribution and workload requirements.

The architecture prioritizes:

* reliability
* mature Linux support
* maintainability
* predictable behavior
* compatibility with backup tooling
* suitability for the workload

The specific filesystem used for each VM should be documented in its deployment procedure.

---

# Backup Considerations

Storage separation simplifies backup planning but does not replace a complete backup strategy.

Backups should distinguish between:

* operating system configuration
* application configuration
* persistent application data
* database data
* infrastructure-as-code state
* secrets and encrypted data

Database workloads should use application-aware or logical database backups where appropriate, in addition to VM-level protection.
Persistent Docker application data should also be included in the backup strategy.
Sensitive data and secrets must follow the project's security architecture and must not be treated as ordinary unencrypted backup data.

---

# Storage and Security

Storage separation is an operational control and should not be confused with a security boundary.
The architecture treats the following as separate layers:

```text
Storage
├── Virtual Disks
├── LVM
└── Filesystems

Network
├── VLANs
├── Firewall Policies
└── Security Zones

Identity
├── FreeIPA
├── RBAC
└── Privileged Access

Secrets
└── OpenBao
```

Each layer provides a different control mechanism.
For example, putting PostgreSQL on a separate logical volume does **not** replace database network segmentation or access control.

# Design Summary

The Enterprise Reference Architecture uses a **two-disk Linux storage model**.

```text
                    Linux VM
                       │
              ┌────────┴────────┐
              │                 │
           Disk 1            Disk 2
          OS Storage       Data Storage
              │                 │
        ┌─────┴─────┐      ┌────┴─────────────┐
        │           │      │                  │
       EFI        vg_os  vg_data        Role-specific
        │           │      │              storage
      /boot      lv_root  │
                           ├── lv_var
                           ├── lv_home
                           ├── lv_tmp
                           └── lv_role_data
```

The resulting standard is:

* **Disk 1:** EFI, `/boot`, and `vg_os/lv_root`
* **Disk 2:** `vg_data`

  * `/var`
  * `/home`
  * `/tmp`
  * role-specific persistent data
* **Database workloads:** dedicated PostgreSQL logical volume
* **Docker workloads:** dedicated application-data logical volume
* **Standard baseline:** 20 GB OS disk + 20 GB data disk
* **Database/Docker:** larger second disk where required
* **No third disk by default**

This model provides a practical balance between **storage isolation, maintainability, scalability, and simplicity** while remaining appropriate for the project's modest hardware environment.
