# Storage Architecture

> Storage design and disk allocation standards for the Enterprise Reference Architecture.

## Purpose

This document defines the storage architecture and disk allocation standards used across the Enterprise Reference Architecture.
The design provides a consistent two-disk model for Linux workload VMs while maintaining a clear separation between the operating system and persistent workload data.

The primary goals are:

* separation of OS and workload storage
* predictable VM deployment
* controlled filesystem growth
* easier backup and recovery
* simplified storage expansion
* efficient use of limited physical hardware
* consistent storage standards across infrastructure roles

---

## Storage Principles

1. **Separate the operating system from workload storage** — Disk 1 contains the core operating system; Disk 2 contains additional system filesystems and role-specific persistent data.
2. **Use LVM for flexible storage management** — Logical volumes provide flexibility for future capacity adjustments.
3. **Keep variable system data away from the OS root filesystem** — `/var`, `/home`, and `/tmp` are located on Disk 2.
4. **Use role-specific storage** — Workload-specific data such as PostgreSQL and Docker application data is placed on Disk 2.
5. **Use a two-disk baseline** — General Linux VMs use two virtual disks; database and Docker workloads may receive a larger second disk.
6. **Avoid unnecessary storage complexity** — Additional virtual disks are not introduced unless there is a clear operational or performance requirement.
7. **Storage separation is independent from network segmentation** — Network isolation is implemented through VLANs, firewall policies, and security zones.

---

# Standard Two-Disk Model

Linux workload VMs follow the following general model:

| Disk | Primary Purpose | Standard Size |
|---|---|---:|
| Disk 1 | Core operating system | 20 GiB |
| Disk 2 | System filesystems and role-specific data | 20 GiB+ |

The **20 GiB** size is the baseline for general-purpose VMs. The second disk should be increased for workloads with significant persistent data, particularly PostgreSQL, Docker, application repositories, and persistent application volumes.

---

# Disk 1 — Operating System

Disk 1 is dedicated to the core operating system.

```text
Disk 1
├── EFI System Partition
├── /boot
└── LVM Physical Volume
    └── vg_os
        └── lv_root
```

The EFI System Partition contains UEFI bootloader files. `/boot` contains kernels and initramfs files. The remaining usable space is assigned to `vg_os` and the standard OS logical volume is `vg_os/lv_root`, mounted at `/`.

The root filesystem is intentionally kept separate from `/var`, `/home`, and `/tmp`.

---

# Disk 2 — System and Workload Storage

Disk 2 contains filesystems separated from the root filesystem as well as role-specific persistent data.

```text
Disk 2
└── LVM Physical Volume
    └── vg_data
        ├── lv_var
        ├── lv_home
        ├── lv_tmp
        └── Role-Specific Logical Volume(s)
```

### `lv_var`

Mount point: `/var`

Contains variable system data such as logs, package caches, service state, spool data, and application-generated system data.

### `lv_home`

Mount point: `/home`

Contains local user home directories.

### `lv_tmp`

Mount point: `/tmp`

Contains temporary files generated by the operating system and applications.

Separating these filesystems limits the impact of unexpected growth on the root filesystem.

---

# Role-Specific Storage

After the standard system filesystems are allocated, remaining capacity in `vg_data` can be assigned to workload-specific logical volumes.

Examples:

```text
vg_data
├── lv_var
├── lv_home
├── lv_tmp
└── lv_pg_data
```

or:

```text
vg_data
├── lv_var
├── lv_home
├── lv_tmp
└── lv_app_data
```

The logical volume name should clearly describe its purpose.

# Database Storage

## db01

`db01` hosts PostgreSQL and therefore requires dedicated database storage.

```text
db01
│
├── Disk 1 — 20 GiB
│   ├── EFI
│   ├── /boot
│   └── vg_os
│       └── lv_root
│
└── Disk 2 — 50 GiB
    └── vg_data
        ├── lv_var
        ├── lv_home
        ├── lv_tmp
        └── lv_pg_data
```

Typical PostgreSQL data mount point:

```text
/var/lib/postgresql
```

The exact PostgreSQL data directory may vary by distribution and version. The architectural requirement is that persistent PostgreSQL data resides on the dedicated `lv_pg_data` logical volume rather than on the root filesystem.

A third PostgreSQL disk is not part of the standard architecture. Additional storage can be introduced later if actual workload requirements justify it.

---

# Application Storage

## app01

`app01` hosts containerized applications and therefore requires persistent application storage.

```text
app01
│
├── Disk 1 — 20 GiB
│   ├── EFI
│   ├── /boot
│   └── vg_os
│       └── lv_root
│
└── Disk 2 — 50 GiB
    └── vg_data
        ├── lv_var
        ├── lv_home
        ├── lv_tmp
        └── lv_app_data
```

A suitable application-data mount point is `/opt/app-data`.

Potential persistent data includes Forgejo repositories, Keycloak data, NetBox data, OpenBao data, Portainer data, Wiki.js data, application configuration, Docker volumes, and other service-specific persistent storage.

# Automation Storage

## auto01

The automation VM hosts Ansible, OpenTofu, automation scripts, infrastructure state, and deployment artifacts.

```text
auto01
│
├── Disk 1 — 20 GiB
│   └── Operating System
│
└── Disk 2 — 20 GiB
    └── Automation-related persistent data
```

The exact additional logical volume should be created only when there is a clear requirement.

# General Linux Infrastructure VMs

Infrastructure VMs such as `ipa01` use the same baseline architecture.

```text
VM
│
├── Disk 1
│   ├── EFI
│   ├── /boot
│   └── vg_os
│       └── lv_root
│
└── Disk 2
    └── vg_data
        ├── lv_var
        ├── lv_home
        └── lv_tmp
```

Additional role-specific storage can be added to `vg_data` when required.

# Storage Allocation

| Workload | Disk 1 | Disk 2 | Storage Focus |
|---|---:|---:|---|
| General Linux VM | 20 GiB | 20 GiB | OS + standard filesystems |
| FreeIPA | 20 GiB | 20 GiB | Identity services |
| PostgreSQL | 20 GiB | 50 GiB | `lv_pg_data` |
| Docker host | 20 GiB | 50 GiB | `lv_app_data` |
| Automation | 20 GiB | 20 GiB+ | Automation data |

The exact logical-volume sizes should be determined according to the VM role and expected workload.

---

# Storage Expansion

The LVM-based design allows storage to be expanded without changing the overall architecture.

```text
Disk 2
   ↓
Physical Volume
   ↓
vg_data
   ↓
Logical Volume
   ↓
Filesystem
```

When additional capacity is required:

1. Expand virtual Disk 2.
2. Resize the LVM physical volume.
3. Extend `vg_data`.
4. Extend the appropriate logical volume.
5. Expand the filesystem.
6. Verify available capacity.
7. Verify the application or service.

For example:

```text
Disk 2
   ↓
vg_data
   ↓
lv_pg_data
   ↓
PostgreSQL filesystem
   ↓
PostgreSQL data
```

The same principle applies to application storage on `app01`.

# Filesystem Standards

Filesystem selection should be based on the Linux distribution and workload requirements.

The architecture prioritizes reliability, mature Linux support, maintainability, predictable behavior, compatibility with backup tooling, and suitability for the workload.

The specific filesystem used for each VM should be documented in its deployment procedure.

---

# Backup Considerations

Storage separation simplifies backup planning but does not replace a complete backup strategy.

Backups should distinguish between operating system configuration, application configuration, persistent application data, database data, infrastructure-as-code state, and secrets/encrypted data.

Database workloads should use application-aware or logical database backups where appropriate, in addition to VM-level protection. Persistent Docker application data should also be included in the backup strategy.

Sensitive data and secrets must follow the project's security architecture and must not be treated as ordinary unencrypted backup data.

---

# Storage and Security

Storage separation is an operational control and should not be confused with a security boundary.

```text
Storage
├── Virtual Disks
├── LVM
└── Filesystems

Network
├── VLANs
├── Firewall Policies
└── Security Zones

Identity
├── FreeIPA
├── RBAC
└── Privileged Access

Secrets
└── OpenBao
```

Putting PostgreSQL on a separate logical volume does **not** replace database network segmentation or access control.

# Design Summary

The Enterprise Reference Architecture uses a **two-disk Linux storage model**.

```text
                    Linux VM
                       │
              ┌────────┴────────┐
              │                 │
           Disk 1            Disk 2
          OS Storage       Data Storage
              │                 │
        ┌─────┴─────┐      ┌────┴─────────────┐
        │           │      │                  │
       EFI        vg_os  vg_data        Role-specific
        │           │      │              storage
      /boot      lv_root  │
                           ├── lv_var
                           ├── lv_home
                           ├── lv_tmp
                           └── lv_role_data
```

The resulting standard is:

* **Disk 1:** EFI, `/boot`, and `vg_os/lv_root`
* **Disk 2:** `vg_data` containing `/var`, `/home`, `/tmp`, and role-specific persistent data
* **Database workloads:** dedicated PostgreSQL logical volume
* **Docker workloads:** dedicated application-data logical volume
* **Standard baseline:** 20 GiB OS disk + 20 GiB data disk
* **Database/Docker:** 50 GiB second disk in the current baseline
* **No third disk by default**

This model provides a practical balance between storage isolation, maintainability, scalability, and simplicity while remaining appropriate for the project's modest hardware environment.
